## Log
- 2026-11-23 tech-lead: WO opened; CT-004 frozen. Existing `coin_refund_redemption` refuses `fulfilled` and any
  redemption with an entitlement (`20261122140000_redemptions_phase_one.sql:31-38`); lane A to decide.
- 2026-11-23 database-engineer (lane A): DECISION — `coin_refund_redemption` is not widened. It refuses a
  `fulfilled` redemption and any redemption with an entitlement (`20261122140000_redemptions_phase_one.sql:31-38`),
  and that refusal is what stops a delivered hazard report being refunded; `db/tests/test_redemptions.py` keeps
  pinning it. A new narrow function `coin_refund_withdrawn_redemption(p_redemption uuid, p_reason text DEFAULT NULL)
  RETURNS uuid` does the DEF-117 refund. Guard (all must hold, else TC013): redemption `fulfilled`; its item
  `is_active = false` (item row read FOR SHARE so it cannot be re-listed mid-refund); item `fulfilment_type =
  'watchlist_slots'` (the only delivery that is a revocable right rather than content already handed over); every
  entitlement of the redemption is `watchlist_slots`; no `product_watches` row uses it (rows locked FOR UPDATE; the
  FK is ON DELETE RESTRICT as a backstop). Entitlement: DELETEd in the same call — `user_entitlements` has no
  trigger and is not append-only, a row means "a right held", and ending it instead would need `ends_at > starts_at`
  games and a reader that filters on ends_at; the deleted rows are kept as a snapshot in
  `redemptions.fulfilment.refund.revoked_entitlements`. Rule that blocked it: `redemptions_chk1`
  (`(status = 'fulfilled') = (fulfilled_at IS NOT NULL)`) forbade `fulfilled -> refunded` without erasing
  `fulfilled_at`; revised in the spec (`Revised`) to `(status = 'fulfilled' AND fulfilled_at IS NOT NULL) OR
  (status IN ('processing', 'failed') AND fulfilled_at IS NULL) OR status = 'refunded'`. No status trigger exists
  on `redemptions`. Ledger: one confirmed `refund` (+spend) with `reverses_entry_id`, idempotency key
  `refund:<spend>` shared with the old function, so neither can pay twice.
