# WO-019 — Redemptions: phase-one items only, nothing left `processing`

Owner: database-engineer (migration + refund function), then community-rewards-engineer (service, tests) · Contract: none
Gate: qa-test-engineer + security-auditor (coins, ledger) · Opened 2026-11-21 by tech-lead
Status: DONE-PENDING-QA — QA PASS, security PASS (2026-11-22); DEF-035 (report access) waits on the human · Size S · Decision: D13 (2026-11-21)

## Why
Six items are on sale (`db/schema-next/seed_reference.sql:58-64`). Only the printable hazard report and extra
watches are phase one (tech doc §2.2). `data_export` and `invoice_discount` take coins and the service never
fulfils them (`backend/app/modules/rewards/service.py:124-133`), so they stay `processing` for ever.

## Scope
- database-engineer: a new migration (spec first) that sets `is_active = false` on every item whose fulfilment
  is not `pdf_report` or `watchlist_slots`, and a `coin_*` function that refunds a redemption (reverses its spend
  in the ledger, idempotent, marks the redemption refunded/failed per the schema's vocabulary). The migration
  refunds every redemption still `processing` for an inactive item. Schema tests for both.
- community-rewards-engineer: the store lists active items only; redeeming an inactive item is refused with the
  existing error shape; no code path leaves a redemption `processing`; a test redeems each active item and sees
  it fulfilled; a test that a second refund does not pay twice.

## Out of scope
The watches feature itself (W5, WO-033) beyond the entitlement the service already grants. Any AWS action:
refunds on the dev host happen when the migration runs at the next release (the human's push).

## Acceptance
- [ ] Only `pdf_report` and `watchlist_slots` items are active after `dbmate up`.
- [ ] A stuck `processing` redemption is refunded once, through a `coin_*` function; a repeat refunds nothing.
- [ ] Each active item redeemed in a test ends `fulfilled`; an inactive one is refused.
- [ ] Gates green; security-auditor PASS.
