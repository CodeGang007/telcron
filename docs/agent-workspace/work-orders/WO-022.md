# WO-022 — Phases 2–3 of the schema promoted to migrations

Owner: database-engineer · Contract: none · Gate: qa-test-engineer + security-auditor (schema) · Opened 2026-11-21 by tech-lead
Status: DISPATCHED · Size M · Decision: D11 (2026-11-21, PLAN §3)

## Why
The backend uses phase 2–3 tables, but they are applied by `make db-next` locally and by a hand-written block in
`infra/aws/deploy-host.sh` on dev, not by dbmate. A fresh database built by `dbmate up` is not the database the
code runs on. Week-2 plan, WO-022.

## Scope
- `docs/database/tools/build_sql.py` (and `schema_spec.py` only if needed) so that `make db-gen` writes phases 2–3
  and their rules and reference seed as dbmate migrations in `db/migrations/`, after `20261121120000`.
- The migrations MUST be safe on a database that already has phases 2–3 (local dev, and the AWS dev host, which
  runs `migrate up` on every deploy): they skip, without error, what is already there. Prove it against the local
  `telcron` database, which has them from `make db-next`.
- `db/tests/conftest.py`, `backend/tests/conftest.py` and the `Makefile` targets `db-next`/`app-db`: build from
  `db/migrations` (+ `db/seeds/001_core_reference.sql`) only. Retire `make db-next` (keep a no-op alias that
  says it is retired if `tools/` or docs call it).
- Docs that describe the db-next step: `docs/database/schema-design.md`, CLAUDE.md lines are tech-lead's — report them.

## Out of scope
`infra/aws/deploy-host.sh` and `.github/**` (infra-deploy-engineer, follow-up — report the exact lines to change).
Any new table or column. WO-019's redemption migration (next pass, same owner).
