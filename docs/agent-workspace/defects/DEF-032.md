# DEF-032 — Every re-screen opens another "Score missing evidence" task for the same product

Found by browser-qa-engineer on 2026-11-22 (WO-017 run 2, local stack @ 706b0f8) · Owner: data-ai-engineer · Severity: S3
Status: FIXED-PENDING-QA

## What happens
Each re-screen whose assessment has insufficient data adds a new `hazard_insufficient_data` review task, even
when an open one already exists for that product. After one e2e run plus this walk, the safety team's queue
holds 12 such cards, three each for the fridge and the charger, with nothing to tell them apart. Each card
says only "Score missing evidence" and the product name (not which dimensions lack evidence).

## What should happen
At most one open task per product (or per hazard assessment that is still current); a new re-screen updates or
supersedes the open task. The card says which dimensions are missing evidence.

## Repro
1. Post a review on a product whose passport has unscored dimensions; wait for the Worker (about 1 s).
2. Repeat with a second member. `select payload->>'product_id', count(*) from review_tasks where
   task_type='hazard_insufficient_data' and status='open' group by 1;` shows one more open row per re-screen.
3. `/review-queue` as admin lists each.

## Evidence

  without looking for an open one.

## Fix
data-ai-engineer, 2026-11-22, branch `week-02`, uncommitted.
- `backend/app/modules/screening/service.py` `_open_insufficient_data_task`: a re-screen with missing evidence
  looks for the product's `hazard_insufficient_data` task in `open`/`in_progress` (by `payload->>'product_id'`).
  If one exists it is reused: `subject_id` moves to the newest assessment and the payload to the newest
  passport (status, assignee and priority untouched). A new task opens only once the previous one is resolved
  or dismissed. The product row is already locked `FOR UPDATE` at the start of `screen_product`, so two
  concurrent re-screens of one product cannot both miss the open task.
- The payload now carries `missing_dimensions` (dimension codes without a valid citation), so the card can
  say which dimensions lack evidence. Showing it on `/review-queue` is frontend-engineer's (not done here).
- Schema: `review_tasks_u1_uidx` is unique on `(task_type, subject_type, subject_id)` while open, i.e. per
  assessment; every re-screen writes a new assessment, so it does not cover this. Not worked around; nothing
  relies on it here.
- Test: `backend/tests/test_insufficient_data_task.py` (two re-screens leave one open task pointing at the
  newest assessment and current passport; after dismissing it through the queue, the next re-screen opens a
  new one). Revert proof: with the lookup bypassed the test fails
  (`AssertionError: assert [UUID('01a1ff...9f8b3168fe1')] == [UUID('01a1ff...777e72c7cfb')]`); restored, passes.
- Gate (lane 55444/63844): `uv run ruff check .` All checks passed! · `uv run pytest -q` 141 passed, 4 warnings in 25.82s.
