# DEF-081 — Two registrations of one new address at once: the loser gets a 500

Found by qa-test-engineer on 2026-11-22 (WO-017 final QA, part A) · Owner: platform-identity-engineer · Severity: S4
Status: FIXED-PENDING-QA

## What happens
`register()` reads `users` for the address (`backend/app/modules/identity/service.py:103`) and, when there is no
row, inserts one (`:108-112`). Two requests for the same new address that arrive together both see no row. The
first insert wins. The second hits `users_email_key` and the API answers **500**: an unhandled
`UniqueViolationError` at `service.py:112` (`await db.flush()`). DEF-043's fix record lists this under "Flagged,
not fixed", but no defect was filed for it.

This also undoes part of what DEF-043 set out to do. Register is meant to answer the same whether or not the
address has an account, and a 500 is a different answer.

## What should happen
The losing request answers like a registration for an address that already has an account: the same 201 body,
and the owner gets the notice (or nothing, under the mail cap). For example, `INSERT ... ON CONFLICT (email) DO
NOTHING` and take the existing-address branch, or catch the unique violation on `users_email_key` inside a
savepoint. Add a test that runs two concurrent registrations for one address and expects no 500.

## Repro
API from `wt/qa-final-a` @ 838beea on a lane DB (`RATE_LIMITS_ENABLED=false`, so the per-address limit does not
mask it). For one fresh address, send three `POST /api/v1/auth/register` requests at once (`curl ... &` ×3, then `wait`).

## Evidence
5 addresses × 3 concurrent requests, status codes per address:
```
201 500 500
201 500 500
201 500 500
201 500 500
201 500 500
```
Server log: `asyncpg.exceptions.UniqueViolationError: duplicate key value violates unique constraint "users_email_key"`
· `File ".../backend/app/modules/identity/service.py", line 112, in register`.
No data is damaged: one account exists, and the database's UNIQUE holds. With rate limits on (the default), the
per-address register limit (5/h) still lets the first few concurrent requests through.

## Fix
platform-identity-engineer, 2026-11-22, branch `week-02` (not committed).

- `backend/app/modules/identity/service.py` `register()`: the insert runs inside a savepoint
  (`db.begin_nested()`). An `IntegrityError` whose asyncpg cause names `users_email_key` rolls back to the
  savepoint only and takes the DEF-043 existing-address branch: `({}, await _notify_existing_owner(email))`,
  so the same 201 `{"email_sent": true, "dev_codes": null}`, no code and no `verification_tokens` row for the
  loser, the owner gets at most the "Someone tried" notice (none over the mail cap). Any other violation is
  re-raised. The loser has already done the argon2 work, so timing matches too.
- Test: `backend/tests/test_identity_hardening.py::test_registrations_racing_for_one_new_address_all_answer_like_an_existing_one`
  runs three registrations with `asyncio.gather`, held by an `asyncio.Barrier(3)` after each request's
  existence read so the race happens every run. Asserts three 201s with identical bodies, one `users` row,
  one verification token, and owner mail = one code + two notices.
- Revert proof: with `service.py` at HEAD the test fails with
  `IntegrityError ... UniqueViolationError ... "users_email_key"`; restored, it passes.
- Gate (lane 55449/63849): `uv run ruff check .` clean; `uv run pytest -q` -> `144 passed, 4 warnings in 31.46s`
  (warnings are Starlette deprecations in `modules/catalogue/router.py`, pre-existing).
