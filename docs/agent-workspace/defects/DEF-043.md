# DEF-043 — Register and sign-in reveal whether an address has an account

Found by security-auditor on 2026-11-22 (WO-017) · Owner: platform-identity-engineer · Severity: S3
Status: FIXED-PENDING-QA

## What happens
`identity/service.py:83-84` register answers 409 `email_taken`; `:178` a locked account answers 423; `:183-184` an unknown email skips argon2 (timing).

## What should happen
Register answers the same for new and existing addresses (the existing owner is emailed instead); a locked account answers like a wrong password; unknown emails run a dummy hash.

Read the cited lines on `week-02` @ 706b0f8.

security-auditor S-4 (Medium), S-12 (Low). Full record: `verdicts/WO-017-security.md`.

## Fix
platform-identity-engineer, 2026-11-22, in `wt-w2-gaps` (branch `wt/w2-gaps`, not committed).
- `backend/app/modules/identity/service.py`: `register` no longer raises 409 `email_taken`; for an address with an account it spends the same argon2 work, creates nothing, and emails the owner a notice ("Someone tried to create a Telcron account with your email"), never a code (a code would let the attacker confirm someone else's account). `login`: a locked account answers 401 `invalid_credentials` (the right password is still refused until the lock ends; recorded as `login_failed`/`locked`); an unknown or inactive address runs `security.verify_dummy` (argon2 against a cached throwaway hash).
- `schemas.py`: `RegisterOut` drops `user_id` (it differed per call). Body is now `{email_sent, dev_codes}` for both. `dev_codes` is null for an existing address, which matters only where `DEV_EXPOSE_CODES` is allowed (local/test, DEF-048).

- Tests: `test_register_answers_the_same_whether_or_not_the_address_has_an_account`, `test_a_locked_account_answers_like_a_wrong_password`, `test_an_unknown_address_costs_the_same_argon2_work`; `test_journey.py::test_lockout_after_five_bad_passwords` now expects 401.
