# DEF-100 — A signed-in member whose API is unreachable is told to sign in

Found by browser-qa-engineer on 2026-11-22 (WO-017 final browser gate, local stack @ 838beea) · Owner: frontend-engineer · Severity: S4
Status: FIXED-PENDING-QA

## What happens
The API was stopped, or requests to it were refused, while a member had a stored session. The members-only
pages (`/wallet`, `/rewards`) show "Sign in to continue · This page is part of your TelcronID" with Sign in /
Create account buttons, and the header shows "Sign in". The session is **not** lost: it stays in
`localStorage`, and once the API is back a reload shows the wallet again. So the screen is the only problem: it
says the member is signed out when Telcron could not be reached. Following it leads to a sign-in form that
also cannot reach Telcron. The public pages handle this correctly now (DEF-036 PASS): product, search and recalls
say "Could not reach Telcron. Check your connection and try again." with Try again.

## What should happen
When there is a stored session and `/auth/me` failed because of the network or a 5xx, `Gate` (and the header)
say "Could not reach Telcron…" with Try again (which calls `reload()` in `useAuth`). They do not offer sign-in.
"Sign in to continue" is only for no session, or a session the server refused (4xx).

## Repro
1. Sign in as any member (local stack).
2. Stop the API (`kill` the API pid in `.dev-logs/api.pid`) or block `http://localhost:4310/**` in devtools.
3. Open `/wallet` or `/rewards` (390 px or desktop).
4. Observed: "Sign in to continue". Restart the API and reload: the wallet is back, still signed in.

## Evidence
- `frontend/src/lib/auth.tsx:24-28`: on a network failure or 5xx, `me` stays `null` (by design, so the session is
  kept), and `loading` becomes false.
- `frontend/src/components/Gate.tsx:10-24`: `!me` → "Sign in to continue", whatever the reason.
- Probe output (API really stopped, phone and desktop the same):
  `{"who":"member","path":"/wallet","reach":false,"text":"DIGITAL WALLET Products you own … Sign in to continue This page i…"}`
  and, with requests refused then allowed again:
  `{"down":"… Sign in to continue This page is part of your TelcronID. Sign in Create account","header":"Telcron Product safety, verified Sign in","sessionKept":true,"afterApiBack":"DIGITAL WALLET Products you own …"}`
- Screenshot: `/tmp/claude-1000/-home-silverblade-Startups-CodeGang-Projects-Telcron-Codebase/f710e93c-b080-41fd-939f-13a2583168e0/scratchpad/final/shots/DEF-100-wallet-api-down-phone.png`

## Fix
frontend-engineer, 2026-11-22.
- `frontend/src/lib/auth.tsx`: `useAuth()` now also returns `unreachable` (the `explain()` text) when a stored
  session could not be checked because of the network or a 5xx; it is cleared on success, on a 4xx and on
  sign-out. The session is still kept, as before.
- `frontend/src/components/Gate.tsx`: with no `me` and `unreachable` set, `/wallet` and `/rewards` show
  "Could not reach Telcron … You are still signed in." with a 44 px Try again that calls `reload()`
  (`role="alert"`). "Sign in to continue" is now only for no session or a session the server refused.
- Not fixed here: the header still shows "Sign in" while unreachable. It is in `Layout.tsx`, which only
  tech-lead edits: when `!me && unreachable`, render nothing (or a small "Offline" chip) instead of Sign in.
- Gates: `cd frontend && npx tsc --noEmit` 0 errors; `npm run build` built in 3.79s. Not walked in a browser.
