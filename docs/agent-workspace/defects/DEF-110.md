# DEF-110 — Search's brand list still reads every product when any brand matches; no test guards the plan

Found by qa-test-engineer on 2026-11-22 (WO-017 last re-check @ bdc4c57) · Owner: catalogue-engineer · Severity: S3
Status: OPEN

## What happens
DEF-080's fix made the name and fragment lists KNN walks of `products_i1_idx`, and DEF-080's index fix added
`products_i4_idx (brand_id, canonical_name, id)`. But the brand list in `_by_words`
(`backend/app/modules/catalogue/service.py:88-91`) joins `products` to the matched brands and sorts, and
PostgreSQL answers that with `Seq Scan on products` over the whole table and a hash join. The new index is
never used by the application. It happens whenever *any* brand matches the words, including common words: `blender`
matches the brand "AquaBlend" (word similarity 0.375), and `len` matches it through `ILIKE`. The docstring
("nothing reads the whole table") is not true for those queries.

Also, no backend test fails if search goes back to reading the whole table: with `service.py` reverted to 838beea,
`tests/test_search.py` is `4 passed`. The four tests guard the answers (typos, fragments, brands, paging), not the
plan.

## What should happen
The brand list reads only `offset + limit` rows per matched brand, as database-engineer proposed in DEF-080
("Fix (index)"): `FROM liked CROSS JOIN LATERAL (SELECT id, canonical_name FROM products WHERE brand_id = liked.id
AND status = 'active' ORDER BY canonical_name, id LIMIT :window) p ORDER BY liked.rank DESC, p.canonical_name, p.id
LIMIT :window`. And a test asserts the plan of the statement `_by_words` sends has no `Seq Scan on products` (for
example under `SET LOCAL enable_seqscan = off`, which the old ILIKE/similarity form cannot satisfy), so a revert goes red.
