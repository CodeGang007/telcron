# DEF-045 — Runtime database role owns the database and every table

Found by security-auditor on 2026-11-22 (WO-017) · Owner: infra-deploy-engineer (+ database-engineer) · Severity: S3
Status: PREPARED — BLOCKED ON HUMAN

## What happens
`infra/aws/deploy-host.sh:125,130`: `telcron_app` is NOSUPERUSER but owns the schema, so it can DROP tables or DISABLE TRIGGER (the append-only rules). DEF-006 item 3 half done.

## What should happen
A separate owner role runs migrations; `telcron_app` has DML and EXECUTE only. Changes the dev database's grants — prepared, applied only with the human's yes at a push.

## Repro
Read the cited lines on `week-02` @ 706b0f8.

## Evidence
security-auditor S-6 (Medium). Full record: `verdicts/WO-017-security.md`.

## Fix
2026-11-22, infra-deploy-engineer. Design only; no script, grant or database changed. Needs the human's yes
(it changes dev's grants, applied by the next release) and database-engineer's review of the grant list.
Survey that shaped it: one schema (`public`); no `SECURITY DEFINER` function in `db/migrations` or
`db/schema-next`; seeds are DML only; `backend/app` runs no DDL, `REFRESH MATERIALIZED VIEW`, `VACUUM`,
`LOCK TABLE` or `SET ROLE` (grep, no hits) — so DML + sequence use + EXECUTE is enough at run time.

## Blocked on human
**Design: a separate owner role `telcron_owner` runs migrations and schema-next; `telcron_app` gets DML + EXECUTE.**
Cost: none (no AWS resource; one new field `OWNER_DB_PASSWORD` in the existing app secret by `PutSecretValue`,
for example `openssl rand -hex 32`, never printed). The owner needs a password because dbmate connects over TCP;
the `pg` helper uses the container's socket.

Order:
1. database-engineer reviews the grant list; the human says yes.
2. Human adds `OWNER_DB_PASSWORD` to the app secret (`PutSecretValue`, no cost) **before** the push — without it
   the deploy stops at "secrets" and the old release keeps running.
3. Take a backup by hand first (`bash /opt/telcron/repo/infra/aws/backup-db.sh`).
4. Push `main`; the release runs the new roles block (REASSIGN), migrations as owner, then the grants.
5. Check: `/health` names the commit; the journey's read and write paths work (sign-in, a review → passport);
   as `postgres`: `select count(*) from pg_tables where schemaname='public' and tableowner<>'telcron_owner'` → 0;
   as `telcron_app`: `alter table auth_events disable trigger all` → permission denied.
Rollback (as `postgres` in `telcron`, then revert the commit on `main`):
```sql
ALTER DATABASE telcron OWNER TO telcron_app;
REASSIGN OWNED BY telcron_owner TO telcron_app;
DROP OWNED BY telcron_owner;   -- only its remaining privileges and default privileges
DROP ROLE telcron_owner;
```
Revert before the next release runs, or the reverted `deploy-host.sh` (which sets `telcron_app` as owner) does
the same on its own: its `ALTER DATABASE … OWNER TO telcron_app` plus migrations would fail on tables owned by
`telcron_owner`, so run the SQL first. The extra secret field is harmless and can stay.
