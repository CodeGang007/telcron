# DEF-012 — "Dismiss" closes a task but leaves its subject stuck: coins frozen for good, a flag pending for good

Found by qa-test-engineer (WO-017, part A) on 2026-11-22 · Owner: community-rewards-engineer (WO-006's owner) · Severity: S3
Status: FIXED-PENDING-QA

## What happens
`resolve()` (`backend/app/modules/moderation/service.py:187`) skips every subject handler when the decision is
`dismiss`, then marks the task `dismissed`. The web queue offers Dismiss on every task
(`frontend/src/pages/ReviewQueue.tsx:84`).
- `fraud_hold` dismissed: the hold stays `open` and its coins stay `frozen`. No open task points at it any
  more, so nothing in the product can release or confirm it.
- `hazard_flag` dismissed: the flag stays `pending`. The reporter can never file another flag on that
  product, because `POST /products/{id}/flags` refuses while one is pending
  (`backend/app/modules/community/router.py:131-134`, `409 flag_pending`).
- `fact_report` dismissed: the report stays `pending` (it is shown as such on the member's rewards page).

## What should happen
Either a dismissal moves the subject to a final state (a dismissed flag becomes `rejected` with no trust
penalty, or a matching status if the schema has one, and a report the same), or `dismiss` is refused
for task types whose subject needs a decision (`fraud_hold`). Which one is the owner's call, with tech-lead.

## Repro
Read from the code paths above; not exercised end to end. The fraud-hold case follows directly from
`coin_resolve_hold` never being called. No test covers `dismiss` (`grep -n dismiss backend/tests` → nothing).

## Evidence
`backend/app/modules/moderation/service.py:184-195`; `backend/app/modules/moderation/router.py:17`
(`Literal["confirm", "reject", "dismiss"]`).

## Fix
By community-rewards-engineer, 2026-11-22, branch `wt/moderation`.

`dismiss` means "closed without a finding", and the subject now always leaves its open state
(`backend/app/modules/moderation/service.py`, `resolve()` and the three `_resolve_*` helpers):
- `fraud_hold` → `coin_resolve_hold(hold, is_fraud => false, actor)`: the hold becomes `released`,
  the frozen coins `confirmed`. Only a finding of fraud (`confirm`) forfeits coins (business rules §2:
  coins are frozen "until a person resolves it"; nothing voids earnings without a finding). Ledger
  touched only through the `coin_*` function; the hold row is locked first and refreshed after.
- `hazard_flag` → `rejected` (`flag_status` has no `dismissed`), reviewed by/at set, note defaults to
  "Closed by the safety team without a finding.", **no trust penalty, no coins**. The reporter can
  flag the product again (no more permanent `409 flag_pending`).
- `fact_report` → `rejected`, reviewed by/at set, no trust penalty, no coins, product unchanged.
- A subject already in a final state is simply left alone by `dismiss` (`confirm`/`reject` still
  answer `409 already_decided`; for holds this also replaces a would-be 500 from the STRICT select).

Tests (`backend/tests/test_moderation.py`): `test_dismissing_a_fraud_hold_releases_the_coins`
(`(0,0,105)` → `(105,0,0)`, hold `released`), `test_dismissing_a_flag_closes_it_without_a_penalty`
(flag `rejected`, trust 10.0, no coins, a new flag → 201),
`test_dismissing_a_correction_closes_it_without_a_penalty`.

Revert proof (dispatch skipped for `dismiss`, i.e. the old behaviour): `3 failed, 7 passed`
(`'open' == 'released'`, `'pending' == 'rejected'` ×2); restored `10 passed`.
Gate: `ruff check .` → `All checks passed!`; `pytest -q` → `103 passed, 4 warnings in 34.55s`.
Frontend: no change needed (Dismiss stays on every task).
