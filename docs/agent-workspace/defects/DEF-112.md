# DEF-112 — A visitor opening the report of a product that does not exist is offered to buy it

Found by browser-qa-engineer on 2026-11-22 (DEF-035 browser verification, local stack @ 37ac599) · Owner: tech-lead
(contract CT-002; producer community-rewards-engineer, consumer frontend-engineer) · Severity: S4
Status: OPEN

## What happens
`GET /api/v1/products/{slug}/report` runs `CurrentUser` before the product lookup, so a visitor gets 401 for any
slug, real or not. The web app turns every 401 into the unlock card. A visitor who opens
`/products/no-such-product-xyz/report` sees "Redeem for 50 TelCoins to unlock", a Sign in button and
"See the free passport" linking to `/products/no-such-product-xyz`, a product that does not exist. A signed-in member
on the same URL correctly gets "We could not find that product" (404).

## What should happen
A visitor on an unknown product should get the not-found answer too, not an offer to pay for a report that
cannot exist. One option: the producer resolves the product before the auth check (the slug is public, so a 404
reveals nothing). That changes the frozen order in CT-002 ("404 … checked before the entitlement", but 401 comes
first), so it needs a tech-lead amendment. The other option is a frontend-only fix: on 401, check the public
`GET /products/{slug}` first. That adds a public read to the report page, which this verification checked was absent.

## Repro
1. Local stack (`make dev`), not signed in.
2. Open `http://localhost:3200/products/no-such-product-xyz/report` at 390 px or 1280 px.
3. You see the unlock card with "See the free passport" pointing at the missing product.
