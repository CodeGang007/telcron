# DEF-080 — Text search scans every product: 230–400 ms at 50 000 products

Found by qa-test-engineer on 2026-11-22 (WO-017 final QA, part A) · Owner: catalogue-engineer · Severity: S3
Status: FIXED-PENDING-QA

## What happens
`GET /api/v1/products?q=<text>` (no barcode or model-number hit) ranks with
`word_similarity(q, canonical_name) > 0.35 OR canonical_name ILIKE '%q%' OR brand ILIKE '%q%'`,
ordered by that similarity (`backend/app/modules/catalogue/service.py:77-84`). Neither form can use the
GiST trigram index `products_i1_idx`, so PostgreSQL reads every product row on every search. The time grows
with the catalogue. `telcron-performance` already lists this under "Known, not yet fixed", but no defect or
work order tracks it.

## What should happen
The fuzzy branch uses the KNN form the index serves (`ORDER BY canonical_name <-> :q LIMIT n`, plus the brand)
as `telcron-performance` says, and the read stays index-backed as the catalogue grows. The schema's own perf case
"Fuzzy product search (trigram)" (`db/tests/test_performance.py`) already uses that form: 19.73 ms at 100 000
products. The application does not.

## Fix
catalogue-engineer, 2026-11-22. Not committed.

**What changed.** `backend/app/modules/catalogue/service.py`: the word branch of `search()` is now `_by_words()`, used
by both the words-only path and the meaning fusion (`CANDIDATES`). The barcode/model exact branch, `_by_meaning` and
the reciprocal-rank fusion are unchanged. Three short lists, each cut at `offset + limit` rows, are merged:
- by name: `ORDER BY canonical_name <->> :q LIMIT n`, a KNN walk of `products_i1_idx`. `<->>` is
  `1 - word_similarity(q, name)`, the same measure the old rank used, so the ranking itself did not change;
- by brand: products of brands with `name ILIKE '%q%' OR word_similarity > 0.35` (rank computed once per brand,
  numbered after the cut so PostgreSQL does a top-N sort);
- by part of a word: `canonical_name ILIKE '%q%' ORDER BY canonical_name <->> :q LIMIT n`, which is the same GiST
  index (Index Cond + Order By). It keeps fragments like "len" in "Blender" (word similarity 0.25).
The outer query keeps the old filter (name ILIKE, brand ILIKE, or rank > 0.35) and orders by `rank DESC`, then by
the position in the list the rank came from.

**Not index-backed: the brand list.** When the words match a brand, the products of that brand are found by
`Seq Scan on products` (~25 ms at 50 000) plus a top-N sort (~50 ms), because `products.brand_id` has no index at all
(only the partial unique `products_u1_uidx (brand_id, model_number_normalized) WHERE model_number_normalized IS NOT
NULL ...`, which a product without a model number is not in). **Request for database-engineer:** an index on
`products (brand_id, canonical_name, id)` (or at least `(brand_id)`, which is also the missing FK index). No index was
added here. When no brand matches, the brand list costs nothing (one row read, then stops).

**Differences from before (say, not hide).**
1. The rank sequence is identical: for 13 queries × offsets 0 and 40 on the 50k DB, the old and new pages have
   exactly the same list of rank values (`same_rank_sequence=True` in all 26). Only *which* products fill a tie, and
   their order inside it, changed: ties used to be alphabetical; now they come in the index's order. Example: q
   `blender`, old first row "Acme Kitchen PowerBlend 1000 Blender" (alphabetically first of ~6 250 at rank 1.0), new
   first "Blender Pro 689".
2. At equal rank, a product found by its own name now comes before one found only by its brand (q `northwind`:
   "Northwind ChillMate Mini Fridge" is now first; before it came after every "Air Fryer Max ..." of that brand).
3. Pages continue each other exactly: 60 rows as one page equal six pages of 10 for all 9 queries checked, ties
   included (each row is placed by its position in the list its rank came from, which does not depend on how far
   the lists were read).
4. An `ILIKE`-only match is still found, but only within the first `offset + limit` such names by similarity; at the
   old behaviour every one of them was reachable at any offset. With `offset <= 10 000` this is the same in practice.
