# DEF-044 — No rate limits on register, verify, resend or sign-in

Found by security-auditor on 2026-11-22 (WO-017) · Owner: platform-identity-engineer · Severity: S3
Status: FIXED-PENDING-QA

## What happens
`identity/router.py:275-315`: with resend every minute and 5 tries per code, ~7,200 guesses/day per address; someone who registered another person's address can brute-force the code to Level 1; unlimited registers relay mail.

## What should happen
Per-IP and per-email limits in Redis on the four routes, a daily cap of codes per address, `auth_events` IP recorded; 429 with the API's error shape.

## Repro
Read the cited lines on `week-02` @ 706b0f8.

## Evidence
security-auditor S-5 (Medium). Full record: `verdicts/WO-017-security.md`.

## Fix
platform-identity-engineer, 2026-11-22, in `wt-w2-gaps` (not committed).
- New `backend/app/core/ratelimit.py`: fixed-window counters in Redis (`rl:<route>:<ip|email>:<sha256>`; addresses hashed). Over a limit: **429 `{"detail": "rate_limited"}` + `Retry-After`** (seconds left in the window). The crossing request writes one `auth_events` row (`login_failed` or `otp_failed`, reason `rate_limited`); the flood after it writes none. Redis down → limits skipped with a warning (the per-code 5 tries and the password lockout still hold).
- Limits (settings in `core/config.py`, env-overridable; `RATE_LIMITS_ENABLED` turns them off): register 30/h per IP, 5/h per email · resend 30/h per IP, 6/h per email (plus the existing 60 s gap) · verify 60/h per IP, 20/h per email · login 60 per 15 min per IP, 20 per 15 min per email · `MAIL_PER_ADDRESS_PER_DAY` 10 (codes and notices; beyond it nothing is sent and the answer does not change). Worst case for code guessing: 10 codes × 5 tries = 50 guesses/day per address (was ~7,200). The browser journey signs up 3 members a run; the backend suite clears the counters per test (`tests/conftest.py::fresh_rate_limits`).
- Client address: `ratelimit.client_ip` believes `X-Forwarded-For` only when the connection comes from `TRUSTED_PROXIES` (default empty), reading hops from the right; an unusable address becomes NULL, never a bad INET. Now recorded on register/resend/verify/login events too (`service.py`, `router.py`).
- Tests: `test_sign_in_is_refused_with_429_after_the_per_address_limit`, `test_each_route_has_a_per_client_address_limit[register|resend|verify|login]`, `test_verify_has_a_per_address_limit_on_top_of_five_tries_a_code`, `test_no_more_than_the_daily_cap_of_codes_is_sent_to_one_address`, `test_the_client_address_is_read_from_a_trusted_proxy_only`, `test_client_ip_walks_forwarded_hops_from_the_right`.
- Revert proofs: login limit call removed → 2 failed; resend mail cap removed → 1 failed; proxy check removed → 2 failed. Restored byte-equal.
- Gate (lane 55444/63844, worktree `wt-w2-gaps`, uncommitted): `uv run ruff check .` → All checks passed! · `uv run pytest -q` → `110 passed, 4 warnings in 21.13s` (95 before; +15 in `tests/test_identity_hardening.py`).
