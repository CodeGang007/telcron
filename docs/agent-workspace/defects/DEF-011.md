# DEF-011 — A moderator can release a fraud hold on their own coins

Found by qa-test-engineer (WO-017, part A) on 2026-11-22 · Owner: community-rewards-engineer (WO-006's owner;
`modules/moderation` is not listed in `telcron-domain-map`, so tech-lead should confirm) · Severity: S2
Status: OPEN

## What happens
`resolve()` in `backend/app/modules/moderation/service.py:186-195` checks "staff cannot decide their own
contribution" for hazard flags (`:113`) and fact reports (`:145`) only. For a `fraud_hold` task it calls
`coin_resolve_hold` with no check on whose hold it is. A moderator whose own earnings are frozen can
open the queue, find their own hold and `reject` it. The frozen coins move to confirmed, and the
fraud control is bypassed by the person it was applied to. `coin_resolve_hold`
(`db/schema-next/phase3_rules.sql:51`) records `resolved_by_user_id` but does not refuse
`p_actor = user_id`.

## What should happen
Refuse with `409 own_contribution`, the same as for flags and corrections, when
`fraud_holds.user_id == staff.id`. Consider also refusing it in `coin_resolve_hold` (database-engineer)
so the rule holds in the database.

## Repro
A throwaway test, run on the QA-a lane and then deleted (it is not committed):
1. `staff_user(client, db, name="Held Moderator")`; insert a `FraudHold` for that user; `coin_apply_hold`;
   `_queue_hold_review` (the same arrangement as `tests/test_moderation.py::test_the_safety_team_releases_a_fraud_hold`).
2. As that same moderator: `GET /review-tasks`, then `POST /review-tasks/{id}/resolve {"decision":"reject"}`.

## Evidence
```
BEFORE {'confirmed': 0, 'pending': 0, 'frozen': 105, 'lifetime_earned': 0, ...}
RESOLVE 200 {"id":"01a1ff74-...","task_type":"fraud_hold","status":"resolved",...,"resolution":"reject",...}
AFTER {'confirmed': 105, 'pending': 0, 'frozen': 0, 'lifetime_earned': 105, ...}
```
Not S1: no coins are created that were not earned. But the held member decides their own fraud review,
which is the control. This needs `security-auditor` (coins, roles).
