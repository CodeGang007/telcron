# DEF-111 — Staff whose API is unreachable are told to sign in on the admin area

Found by qa-test-engineer on 2026-11-22 (WO-017 last re-check @ bdc4c57, code review) · Owner: frontend-engineer · Severity: S4
Status: OPEN

## What happens
DEF-100 taught `Gate` and the header about `useAuth().unreachable`. The admin area has its own gate,
`frontend/src/pages/admin/AdminLayout.tsx:16-36`, which reads only `{ me, loading }`. A staff member with a stored
session whose `/auth/me` fails on the network or a 5xx gets "Sign in to continue · This page needs a signed-in
account" with a Sign in button on `/admin/review-queue`, `/admin/data-sources` and the rest. This is the screen
DEF-100 removed from `/wallet` and `/rewards`. The header above it now says "Offline", so the page contradicts the header.

## What should happen
Same as `Gate`: with `!me && unreachable`, show "Could not reach Telcron … You are still signed in." with Try again
(`reload()`), not the sign-in prompt. The `Unreachable` block in `components/Gate.tsx` could be exported and reused.

## Repro
1. Sign in as a moderator or admin (local stack).
2. Stop the API, or block `http://localhost:4310/**` in devtools.
3. Open `/admin/review-queue`.
4. Expected from code: "Sign in to continue". Not walked in a browser in this run.

## Evidence
- `frontend/src/pages/admin/AdminLayout.tsx:16` `const { me, loading } = useAuth();` and `:25-36` `if (!me) return …
  "Sign in to continue"`.
- `frontend/src/components/Gate.tsx:38-40` has the `unreachable` branch; `AdminLayout` does not.
